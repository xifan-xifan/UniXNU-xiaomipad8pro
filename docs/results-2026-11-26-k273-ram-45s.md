`tooling/native/run-console-ram-k273.ps1` (this repository, added today) drove the whole
cycle off one `fastboot boot` of `out/k273-ram/boot-piano-macos-ram-A-bundled.img`

## The mailbox of this build needed a different stride, and the old stride decoded to noise

`tooling/native/xnu-log.py decode` voted the new dump down to noise: it took
`cap = (size - 256) / 11 = 667252` from the dump length, the copies at that stride
agreed on nothing, and the adaptive threshold fell to 3 of 11. The kernel's own line
says what the region is:

    pstore-console: mirroring the console to 0x9cb00000 (+0x6f0000), 150 early bytes

0071 (`PRR_BYTES`) carves 64 KiB of the region out for the retained reset reason, and
0058 made the header 256 bytes, so this kernel mirrors with
`cap = (0x6f0000 - 256) / 11 = 661294`. The 0054-era image that filled the same address
on the 26th morning has no 0071 and really does use 667252, so the stride cannot be a
constant: `xnu-log.py` now reads it from the mirroring line held in copy 0 and keeps
whichever stride the copies agree on, with `decode FILE STRIDE` as an override. Re-run
over both dumps: 661294 for the new one (threshold 6, clean text) and 667252 for the
morning one, unchanged.

`84581E99-85BE-4957-AC53-2947E887B3E4` is the 27.3 OS volume of
`out/inputs/k273/root/root.json`, read out of `linux_rootfs` through the root window
(`native-ufs-root=1 native-ufs-root-part=linux_rootfs`), with `data-persist=0` so NativeRamBlock
kept Data in its 2048 MiB volatile budget. `hfs_mountroot failed: 13` is the kernel
trying HFS before APFS, as it does on every native root; `Image4` nonce and root-hash
complaints are the expected absence of iBoot forwarding.

The point of the run was the death of the older collection, and it is not there. The
`9f276dff` set (k27 0054 era plus the 200 in-place patches) died at
`mac101: initbsd AMFI thread run` with an AMFI `autda x16, x17` PAC fault at
`AppleMobileFileIntegrity __TEXT_EXEC+0x4f3e8` and a MACH reboot. This console reaches
swap startup, past the security-policy registration and past the root mount, with no
fault of any kind, and the last line is the guard's own 45 s deadline. It is a live boot
that ran out of window, not a boot that ran into a wall.

The window is the whole story: `docs/boot-time.md` section 2 puts the first WindowServer
frame at T 105-113 s and the lit login frame after that, and those numbers are for a
persistent Data store; this one carries a volatile store and spent 2.3 s of its 45 in the
two UFS window matches alone. The next image is the same assembly with
`PIANO_RESET_AFTER=420`, which keeps `piano-reset-to=bootloader` and so still returns
itself to ABL for the reader to dump.
