# XNU USB diagnostic on the tablet

Stock ABL accepted temporary image `a711c1885a407d7630b3892e9f871ff6fcb7e3039a08514bd67a1141ce7f6da6` with slot A successful, bootable, six retries and no update snapshot. The sole FAT file change from the prior control was `piano-usb=2` in the default entry. The independent Windows PnP observer ran before the trial and saw Android `18d1:4e11`, two intervals of `18d1:d00d`, and Android again at 06:23:33 local host time. It did not sample `1209:0001` during the transition. No host reboot command followed the temporary boot.

HyperOS OS3.0.309.0.WPYCNXM returned on `_a` with boot completed and boot reason `bootloader`. The boot ID changed from `6be28244-f876-4b70-83ec-53d8c1e7fe67` to `61fe4d4d-d129-4c65-8713-c7fa97610b16`. The USB result does not distinguish loader failure, early XNU failure, device controller setup failure or an enumeration missed between samples. Do not rerun this profile without a new witness. Qualify a checkpoint before IOKit and its retrieval across reset. Raw evidence: `out/watchdog-enter-usb-live/`.

The Windows observer reached its normal end. A retrospective query of the 06:21:37–06:24:00 local window found three Kernel-PnP Device Management events with the Android/fastboot VID, no `VID_1209` record, and no events in Kernel-PnP Configuration or DeviceSetupManager Operational. These logs have limited coverage and do not rule out brief enumeration. Stock ADB reports boot complete but cannot read `/sys/fs/pstore` with its current shell permissions. The previous full CVP dump still decodes as `no XNU log (signature 0x1106)`.

The frozen KC contains `pstore-console`, `piano-reset-to`, `piano-reset-after` and `piano_set_restart_reason` strings. Patch 0057 shows that `piano-reset-to=bootloader` writes a PMIC SDAM restart reason, so it is not a pure RAM option. It offers a way to reach ABL and read CVP before HyperOS runs if the XNU startup hook executes; a pre-hook failure would still take the existing watchdog path. Before that diagnostic, qualify the pre-Android retrieval sequence with a known RAM record and identify how the restart reason clears. Do not interpret a missing record in the post-HyperOS dump as a failed XNU entry.
