# Piano DPU M3 high refresh

On the y12o qualification boot, both panel links verified 60.043 Hz after 120 → 60. The subsequent 60 → 144 request reached the
underrun check, as did its rollback. The existing console message establishes a DPU underrun in each observation interval.
It has no per-interface mask or frame timestamp. See [the original qualification and rollback analysis](dpu-m3.md#y12o-qual1-underrun-and-login-failure).

Linux votes AB once per **acquired memory path**. It sums the plane fetch budgets, applies 120%, divides by the path
count and sends the catalog DRAM IB to each path. The 35-line plane prefill allowance is absorbed by the 106 lines
after VFP. The SM8750 path is `MASTER_MDP → MNOC_HF → GEM_NOC → LLCC → EBI` (MM0, SH0, ACV/MC0). MDSS runtime
resume also holds an independent 0 / 400,000 kB/s enable request on that path. RPMh aggregates the requests.
The Ubuntu simplefb OPP is a different, fixed vote of **3,280,896 / 4,257,792** kB/s for inherited 120 Hz.
PianoDpu's identically valued constants describe that DT OPP. PianoA830's DDR idle floor is a shared floor sized from
the 120 Hz payload. Neither gives a measurement of the display's NoC allocation. Android's CESTA consumers include six
hardware and one software display voters on MMSS NoC and MC Virt. The DT describes topology and floors. The live votes
also depend on enabled layers, source format, compression and the active CRM client.

## Ranked causes and read-only checks

1. **Core or fabric capacity.** Each link still consumes 6,400 uncompressed bytes per line. The two halves need
   3.548 GB/s at the 60/120 line rate and 4.258 GB/s at 144, before margin. A 105% per-half clock proxy moves
   from 465.696 to 558.835 MHz. A 532 MHz inherited clock or a 120-sized bus allocation could therefore be
   sufficient for 120 and miss deadlines at 144. This is a sizing model. The Linux full-CRTC OPP calculation
   is already capped at 575 MHz in both modes. The absence of a native vote is confirmed, and its impact
   depends on the actual boot allocation.
   - Capture active `disp_cc_mdss_mdp_clk` and its parent in stock and Ubuntu `clk_summary` at stable 120 and
     144 with the same workload. For native 60 and 120, read RCG CMD/CFG at DISPCC +0x8150/+0x8154 and,
     with the existing clock-access gate open, PLL0 status and L/ALPHA at +0x0c/+0x10/+0x14.
   Source 1/HID 5 is divide-by-3 at several OPPs. The Taycan ELU parent rate is
   `19.2 MHz × (L[15:0] + ALPHA[15:0]/65536)`. Confirm the PLL is locked before using it.
   Compare the MMCX level and any CESTA ownership alongside it.
   - Pair the clock read with Linux `interconnect_summary` and the stock ICC/CESTA applied votes for each display
     client. Record average and peak for MMSS/HF, LLCC and EBI across the same intervals. For native use only
     vetted readable CESTA or RPMh/BCM state for MM0, SH0 and ACV/MC0, including the active display voter.
     Report an unavailable voter as unknown. The GPU DDR floor and the Linux simplefb request cannot answer it.
2. **VIG/VBIF service latency.** Compare VIG0/1 FETCH_CONFIG, DANGER/SAFE, CREQ low/high and QOS_CTRL (SSPP offsets
   +0x48, +0x60/+0x64, +0x74/+0x78 and +0x6c). With VBIF accessible, compare pending/source errors, RT remap
   and XIN 0/4 read-limit bytes (low bytes of VBIF +0xb0/+0xb4). Capture both INTF fetch starts and CFG bit 31.
   Matching clean-window clocks with increased VBIF pressure or different boot versus stock QoS would raise this candidate.
3. **Timing/group handover.** A shorter HFP plus the panel's B2/B3 change introduces two latches and a panel handover.
   An error restricted to the first frame, with clean subsequent frames at adequate clock and fabric votes, would
   raise this candidate. Correlate live INTF1/2 frame/line, CTL FLUSH, DSI shadow/ACK and each raw/IRQ-sticky
   underrun bit around the latch, the HS command and steady observation. Use the existing M1 read-only
   `machdep.piano_dpu_snapshot` at least 100 ms apart on already-running 60/120 profiles. Compare matched idle
   and moving windows and count flip/watch underrun log events against successful flips. In the M1 captures
   login, idle and moving at 120 all read TOP0 status `0x28000300`, with bits 26/28 clear. The per-INTF
   `0xa00` status and frame/line counters are raw status and position data. M1 has no cumulative underrun counter
   or 60 Hz comparison. Qual1's bounded clean 60 check is the available control. Sticky bits can be consumed by
   IRQ or flip handling, so isolated snapshots cannot give event totals.

## Fix-image gate

Path: WindowServer/QuartzCore 27.3 digital-out mode and refresh query → IOMFB timing IDs and slot 423 → NativeGopDisplay
startup request → PianoDpu worker under the flip transaction lock → inherited VIG/LM/DSC and bonded CTL/INTF/DSI → P81.
Sheng supplies the read-only CTL/counter reference. Ubuntu MSM and stock P81 supply the hardware sequence and limits above.

Checks: Geometry, awake video engines, clock branches, bonded CTL route, live counters, latch/timing readback and
bounded underrun verification are **ours-OK** for the existing transaction. The applied MDP/ICC/MMCX rates and per-mode
VIG/VBIF pressure are **unknown**, with display-specific votes **ours-missing**. Exact stock-to-native HFP/panel latch
alignment is **unknown**. A fixed-120 qualification needs both INTFs at 120, exactly one 120 Hz IOMFB timing and fixed refresh
interval, sustained delivered swaps at the requested cadence, and no underruns under idle, motion and resume.

Root cause: The 144 transition saw an INTF underrun with a 20% higher line-feed demand and no new native display-resource
request. Capacity, service latency and handover remain ranked candidates. Retain the 144 fix-image hold until powered
measurements distinguish them and identify the required resource or sequencing change.

ONE change: Allow a fixed verified 120 Hz boot contract with `piano-dpu-modes=120`. Reuse inherited 120 scanout or
the same-group VFP transaction from 60. Publish the sole observed timing after success or verified rollback, and withhold
publication on an unverified 120 request. `piano-dpu-modes=1` keeps the 60 Hz path. The 90 Hz plan has a lower line rate
but still changes HFP and the panel rate group, so 90 and 144 stay outside the native publication/selection path pending
hardware qualification. The timed model must cover inherited 120, the VFP return, rollback and rejected rates.
