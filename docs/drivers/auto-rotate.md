# LT-C3 automatic display rotation

The existing path has two hardware checkpoints. The `sens-island5` RAM run received LSM6DSO accelerometer samples through the ADSP and published `top` in the stand pose. The same run verified that the ambient-light stream reached PianoBacklight and applied its first target. The `touch-native3` RAM run used `piano-rotated --set 90` and read back 90°, then returned to 0°. A 90° native touch test in `touch-native2` established that BackBoard expects panel axes. Physical, detached auto-rotation through all four edges still needs a RAM run.

## End-to-end checks

| Step | Status | Evidence |
| --- | --- | --- |
| LSM6DSO → ADSP SSC | **ours-OK (RAM)** | PianoPower owns the running ADSP. PianoSensors serves the sensor process's pack through FastRPC, discovers SSC service 0x190 and looks up the default `accel` SUID. See [sensors.md](sensors.md) §§3–5c. `sens-island5` verified request 513 and the first accelerometer vector. ALS request 514 shares the hub and uses its own client. |
| SSC → PianoSensors | **ours-OK (source, host, RAM bench)** | `SensorsStream.c` sends 513 at 10 Hz by default on its own QRTR port. QMI reports 0x21/0x22 carry a SUID and events. Event 1025 carries fixed64 QTimer ticks and at least three float components in m/s². The parser checks length, SUID and stream state before using a sample. Session restart, guard strike, sleep and the display gate are exercised by the host stream tests. Physical detach and reattach in ordinary acquisition mode are **unknown**. |
| Sample → candidate edge | **ours-OK (host, stand pose on RAM)** | `SensorsPolicy.c` converts the SSC up vector to fixed-point down gravity and applies `a+y+x+z`. With the default map, SSC +X, +Y, −X and −Y are top, left, bottom and right. Top is measured and the two side signs remain **unknown** on physical hardware. `SensorsOrient.c` accepts 0.6–1.4 g, requires a 1.3× leading-axis margin at diagonals, and after a 250 ms hold publishes a new state. Face-up and face-down map to edge `none` and leave the display at its current angle. |
| Timing of the 250 ms hold | **ours-missing at baseline (host reproducible)** | `ss_receive` gives every event in a report the same receive time. Two matching samples separated by a long outage can complete a hold, and a batch spanning 250 ms of measurements cannot complete it on its own. The QTimer value is already decoded by `ssc_events_next`. |
| Edge → `piano-rotated` | **ours-OK (source and host policy)** | `PianoSensors.cpp` publishes `piano-sensors-edge`, then `piano-sensors-seq`, and sends a property-change message on edge changes. The agent also polls the sequence every 250 ms when the panel is awake and the cover is detached (every 5 s when asleep). `AutoRotate.c` and `ps_rotation_step` require a further 600 ms of edge dwell and a 1 s minimum between rotations. Face-up/down resets the pending edge. The `Locked` preference holds the angle and a manual rotation holds until the edge changes. Delivery in a real detached session is **unknown**. |
| Userland and profile | **ours-OK (packaging source), ours-missing in the recorded v13.1y12c profile** | `configs/userland.toml:195–213` stages the agent and its global LoginWindow/Aqua LaunchAgent by default. The recorded profile reported `piano-rotate=0`, so the agent exited successfully. The accompanying forced and docked acceleration settings were for bench acquisition. The normal combination for the native digitizer is `piano-sensors=4 piano-sensors-rotate=1 piano-rotate=2`. |
| Agent → WindowServer | **ours-OK (manual 0°/90° RAM)** | `piano-rotated.m` finds the panel by vendor/model, checks the MonitorPanel `MPDisplay` method encodings and `canChangeOrientation`, then invokes `setOrientation:` from a live console session. `CGDisplayRotation` is the public read-back. The agent verifies the angle within 2 s, backs off on failure and gives up after five failures. Automatic requests through the agent and 180°/270° on the tablet are **unknown**. |
| WindowServer → scanout | **ours-OK (manual 90° RAM), unknown (rendering-angle call and rotated flip eligibility)** | The 27.3 decoded cache has MonitorPanel's `MPDisplay`, SkyLight's `SLSSetDisplayRotation`, CoreDisplay's `CGXSetDisplayRotation` and `IOMobileFramebufferSetRenderingAngle`. Prior symbol analysis in [sensors.md](sensors.md#5a1-display-rotation-the-mechanism-verdict) identifies the IOMobileFramebuffer family's inherited rendering-angle hook. `NativeGopDisplay.cpp` submits through that family and presents through its copy or PianoDpu flip path. The observed portrait desktop establishes that scanout works at 90°. The exact rendering-angle calls, swap surface layout and choice of copy/flip in each orientation still need runtime evidence. |
| Raw touch → panel axes → desktop | **ours-OK (host and 90° RAM), unknown (physical corners in all four rotations)** | `TouchMatrix.h` maps input to the fixed 3200×2136 panel. An explicit `piano-touch-flip` takes priority over the build's `PIANO_TOUCH_INVERT_Y`, then calibration, then panel defaults. The native Touch Screen binds to the internal display's `IOMFBUUID` and by default sends panel coordinates. BackBoard rotates them for the displayed desktop, as observed in `touch-native2`. Agent level 3 and `piano-touch-rotate=1` are for the separate desktop-axis path, with `pat_rotate` latched at touch-down. Use agent level 2 with the native panel-axis path. See [touch.md](touch.md#187-the-binding-by-itself-and-the-axes-touch-native2-2026-11-23). |
| Keyboard cover → landscape | **ours-OK (source and host), unknown (physical attach from portrait)** | `PianoKeyboard.cpp` publishes the MCU attach bit as `piano-keyboard-attached` and notifies clients. The agent's default `piano-rotate-cover=2` returns to 0° subject to the minimum interval and holds landscape. Detach applies a 1.5 s hold before a new edge can settle. The kernel normally stops acceleration while attached. The hall/lid input is distinct from the attach bit. |

The remote `sensors/rot1` branch contains the optional raw-vector property (`17d30be3`), manual-rotation notes (`c6651288`), and a foreground `--cover` override (`76af7f35`). Those commits are outside the baseline of this change. The existing boot controls and `TestEdge` provide the test path on this branch.

## Host verification

`package/PianoSensors/tests/run-host-tests.py --only orient --only piano --only streams --only kernel` exercises synthetic gravity and QMI report streams. The A/B cases cover the same four edges and flat hold with both clocks, plus a single batch with enough source-time dwell, a gap over the limit, missing and duplicate timestamps, time reversal, and retention of the last accepted edge. `package/PianoAuto/tests/run-host-tests.py` covers agent settle, cover/lock policy and display read-back handling. `package/PianoTouch/tests/touch_native_host.cpp` checks native HID reports at all four corners at each angle in both coordinate modes. `touch_host.cpp` covers the earlier panel Y correction. The host digitizer model ends at the event coordinates, before BackBoard's transform.

## RAM-boot read list

1. Prove the running build and the GUI session. Record the actual boot args, linked PianoSensors, the staged sensor pack, and the `piano-rotated` executable and LaunchAgent. Use a volatile RAM configuration. Read `kern.piano_bootargs`, `launchctl print gui/<uid>/com.unixnu.piano-rotated` and `piano-rotated --probe` from the console user's session. Require the internal display, `canChangeOrientation 1`, rotation lock off, an awake desktop and native touch bound to the same display. Keep a time-bounded console and agent log and verify both contain a known-positive line from the boot.
2. For a real sensor run use `piano-sensors=4 piano-sensors-rotate=1 piano-rotate=2 piano-sensors-accel-sample-time=1` with native touch and panel axes. Read `piano-sensors-{streams,edge,seq}` with `ioreg -r -c PianoSensors -l` and `piano-keyboard-attached` with `ioreg -r -c PianoKeyboard -l`. Match the opt-in boot line, 513 enable, observed rate, first sample, growing `streams.accel` sample counter and edge transition to the agent's `edge up`, `rotate … asked` and `display … shows` lines. Read the raw vector property if the build includes the separate `sensors/rot1` diagnostic. Read ALS status and its backlight target as the shared-hub control.
3. In one attended pass detach the cover and hold physical top, left, bottom and right edges upright until the agent reports 0°, 90°, 180° and 270°. Hold face-up and face-down and move near a diagonal to check that the picture holds. Start in portrait, attach the cover, and check `attached=1`, stream stopped, and landscape held at 0°. Detach and check a fresh session and the 1.5 s hold. Use the C920 during all physical pose changes to capture the panel, cover and upright content. Compare CoreGraphics read-back and desktop width/height with the physical picture. Save NativeGopDisplay swap dimensions and flip/copy counters when available.
4. If the tablet cannot be turned unattended, use the existing injection on a diagnostic RAM profile with `piano-rotate=2 piano-rotate-test=1 piano-rotate-cover=0`. In the active console user's GUI session set `defaults write com.unixnu.piano-rotated TestEdge -int N` then `notifyutil -p com.unixnu.piano-rotated.prefs`. Use 0, 1, 2, 3, 0 with at least 4 s between steps, plus `-1` for no edge. Record the agent's test-edge marker, requests, read-back and C920 view. With a parallel sensor bench check, `piano-sensors-rotate=2 piano-sensors-accel-cover=1` may keep sampling while docked. The injection qualifies the userland/display leg. Real-axis signs, continuity under live SSC, and the physical cover transition still need the sensor pass.
5. After each displayed angle settles, tap four labeled, inset corner targets and keep the C920 view in the tap window. For physical panel positions TL, TR, BL, BR, the expected desktop targets in that order are `TL TR BL BR` at 0°, `TR BR TL BL` at 90°, `BR BL TR TL` at 180°, and `BL TL BR TR` at 270°. Record 16 touch results and read `machdep.piano_touch_native` for native mode, panel axes and errors. Existing `touch-inject` support can exercise the event path at the same points where physical taps are unavailable. Physical taps are needed to qualify `PIANO_TOUCH_INVERT_Y` and calibration.
6. Return the tablet to its top-edge-up or docked pose. For injection, set `TestEdge` back to 0 first. Restore display angle 0° in the console session with `piano-rotated --set 0`, verify the view and angle, and clear the temporary `TestEdge` preference if used. Record simulated and physical evidence with the boot's provenance.

## Fix-image gate

Path: LSM6DSO → ADSP SSC/FastRPC → QRTR QMI 0x190 and event 1025 → PianoSensors sample-time dwell and edge/sequence → piano-rotated cover/lock/settle → MonitorPanel and WindowServer → CGDisplayRotation read-back and NativeGopDisplay scanout → display-bound native touch in corrected panel axes, rotated by BackBoard.

Checks: RAM evidence covers acquisition in the bench profile, ALS delivery, the stand edge, manual 0°/90° display rotation and a native touch at 90°. Host checks cover orientation and cover policy. Exact live SSC timestamp cadence, physical side-edge mapping, four-corner checks, real cover transitions, consumer delivery and rotated swap/flip behavior remain to be read on RAM.

Root cause: The recorded v13.1y12c profile supplied no rotation consumer because `piano-rotate` was disabled. Independently, the sensor filter uses the AP's receive time, which gives batched samples one time and lets a stalled stream satisfy the pending 250 ms hold. The latter is reproducible with synthetic SSC reports and is the code defect selected here.

ONE change: Add `piano-sensors-accel-sample-time=1` (default 0) to run the existing 250 ms orientation hold on SSC QTimer timestamps. Reset the pending candidate on a zero timestamp, time reversal or a gap over two requested sample periods (200 ms at 10 Hz). Ignore duplicate timestamps and keep the last accepted orientation across timing discontinuities.
