# Wi-Fi radio toggle and auto-rejoin on y12l

Installed y12l recovered scanning after the radio was switched back on, then remained disconnected without a SET20 association request in the retained console window. Native boot requires a fresh SET20 from airportd before the station will attempt a join. The exact airportd decision remains open, so this analysis does not clear the fix-image gate.

## Evidence from the installed run

- The phase transcript shows `machdep.piano_wifi_ps` changing from 0 to 1 and back. The first OFF followed the PS=0 write in the same shell command. The radio stayed off through two Bluetooth scan phases, roughly two minutes. Twenty seconds after the first ON, the restore command reported `status: inactive` and PS=0. The run summary records no recovery after more than five minutes, a second off/on and a `piano-wifi-join` kickstart. A reboot restored Wi-Fi.
- The saved post-toggle console begins during level 6. It records firmware ready, STA vdev 0 handed off to level 7, event 55 with `available 1` and `248 -> 0`, and a firmware background scan growing the list from 15 to 18. Airportd then read scans 18–27 to completion, 18 records each, with the usual end-of-list errno 5. GET103 returned errno 2 (`ENOENT`, no current association). The window contains no SET20 receipt, ASSOCIATE refusal or station start. The console lacks the lead-in, the underlying airportd decision and the helper's own transcript. The Bluetooth packet capture in the same run came from a different day and supplies no Wi-Fi timing evidence.
- `power on (4 set(s))` is the current GET19 view plus a cumulative count of SET19 payloads that passed parsing. The increment precedes the driver's power operation and its return code. The same summary reported zero requests answered by the accept mode and zero event-post errors. The separately passing installed `wifi_rejoin_gate` covers one five-second OFF interval with no PS writes. It leaves the long OFF and repeated cycle untested.

## Join-helper receipt

`configs/userland.toml` stages the default-on `com.unixnu.piano-wifi-join` one-shot. After `piano-airportd-kick.sh` observes the current airportd PID adopting the interface, it atomically publishes `/var/run/piano-airportd-kick` with the current boot UUID and starts the helper. The helper probes the profile sysctl, safely opens the root-only profile, checks the marker's root ownership, mode and UUID, then requires `machdep.piano_wifi_native_boot=1`. A missing, invalid or different-boot marker blocks the helper. The marker stays valid across Wi-Fi state changes and serves as evidence of boot-time adoption.

The join receipt itself lives in the kernel profile store. After valid Apple80211 SET20 input passes the driver's power gate, `piano_wifi_net_menu_join_profile` installs the profile under `gProfileLock`, sets its source to `apple-set20`, increments `gProfileGeneration`, and accepts that generation in `WifiJoinRequest`. This happens before a station attempt, authorization or DHCP. The read of `machdep.piano_wifi_join` prints the retained profile's generation and source. The helper's `receipt()` accepts any nonzero generation with `source apple-set20`. After the 35 s native grace, the default helper uses that receipt before testing location readiness, checks it again before the scan and before CoreWLAN association, and also skips on CoreWLAN's reported association. A separate before/after read of the raw generation confirms a fresh SET20 following a successful CoreWLAN API call.

An accepted SET20 replaces the previous generation. Clearing the profile in `stopRadio` removes the readable receipt, and a new boot starts with an empty store. SET19 OFF and SET22 cancel the request's result without clearing its profile or generation. SET19 ON can reopen power permission without creating a generation. Involuntary loss takes down the station without clearing the retained profile. With the default `piano-wifi-sleepoff=2`, suspend parks the radio and the wake restart preserves the profile. In all three cases, a same-boot helper invocation can skip with no live station or pending join. Sleep with `piano-wifi-sleepoff=0` can preserve the link, in which case skipping is correct, or expose a loss on wake, in which case the old receipt still suppresses the fallback. A PS write only changes the station's requested doze mode. A PS toggle with a surviving link should suppress a duplicate. A PS toggle followed by loss or OFF/ON leaves the same stale receipt. The installed run does not establish that PS caused the loss or that the helper took this particular exit.

The Apple80211 association snapshot is a kernel interface. The existing userland sysctls expose ownership and acceptance history. The host-side change is gated by `piano-wifi-join-current=1` (default 0) and registers read-only `machdep.piano_wifi_join_current` to report the active SET20 generation or 0. A pending request counts within its deadline on the radio pass that accepted it. A successful request counts on the pass that authorized its matching station for as long as that association is live. The existing user stop/cancel state and the driver's restart count invalidate the receipt across OFF/ON and parked sleep. Reported link loss invalidates it on the same pass. The helper uses the current generation for duplicate suppression, including its final check before association. The helper still compares the raw SET20 generation before and after the API call to confirm a new request. The adoption job or an explicit kick still starts one invocation with the existing provisioning, power and location checks.

## Fix-image gate

Path: `networksetup` → CoreWLAN/CoreWiFi XPC → airportd → Apple80211 GET/SET19 and optional SET22 → PianoWifi stop/restart → fresh STA vdev and scan → power/availability/cache events → airportd admission, candidate and credential → Apple80211 SET20 → station auth/association → supplicant keys → authorized link and DHCP. The separate PS path runs from the root sysctl to the authorized STA's WMI parameters and PS_MODE.

Checks: ours-OK for power/scan transport, fresh level 6/7, event 55 ON post, native join ownership and the known-good association chain. Ours-missing for retry after a failed event 55 post and for current association validation in the default helper path. Unknown for the PS=0 send before OFF, event 55 receipt during both cycles, airportd admission, current target eligibility and credential lookup in this run.

Root cause: the failed window stalls before SET20. The native ladder remains idle without a new generation, and the boot helper can skip on an earlier association's receipt from the same boot. The opt-in host change addresses the helper gate. The airportd gate that blocked a new SET20 remains unknown pending the paired capture above.
