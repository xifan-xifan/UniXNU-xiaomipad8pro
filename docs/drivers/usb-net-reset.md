# USB network resets during tablet-to-Mac transfers

On installed v13.1y12m (2026-11-26), one SSH stream over IPv6 link-local on the USB interface delivered all of 64, 256 and 512 KiB. The 1 MiB pull delivered 688,128 bytes and the 4 MiB pull delivered 262,144 bytes before the Mac reported `Connection reset by peer`. The larger failures repeated. Small transfers and interactive SSH could run for hours. On installed y12l, a roughly 260 KB stream reset at its end. These are the supplied observations. The byte counts measure application payload; they give neither TCP sequence numbers nor NTB boundaries. The source audited here is y12m checkout `8262890b`.

**Confirmed on installed v13.1y12m:** The 64 KiB PianoUsbNet TX frame ring saturates during unpaced pulls. The driver drops frames and its direct legacy output callback can surface the drop as `EPERM` to the writer. A paced pull completed on the same boot with no additional drops.

The complete `usb` monitor replies bracketed the two short pulls with `drops: send` rising from 0 to 825 and zero bad lengths. The link and interface stayed up, the registry entries stayed stable, and USB events and IN NTBs kept advancing. The capture showed no controller reset, stall, disconnect, overflow or recovery markers. The paced control advanced IN NTBs with send drops flat at 825. A fresh SSH command worked after the trials. These reads close rank 1 as the cause of the transfer cuts. The `sshd` window did not capture an `EPERM` line, and the exact TCP close/RST sequence remains unobserved.

## End-to-end path on installed y12m

1. **Publish.** With `piano-usb=2 piano-usb-net=1`, [PianoDwc3](../../package/PianoDwc3/PianoDwc3.cpp#L2868) allocates the network queues and starts the network thread. The thread waits for IOBSD and attaches [PianoUsbNet](../../package/PianoDwc3/PianoUsbNet.cpp#L54), an `IOEthernetController`, beneath PianoDwc3. It publishes an `IOEthernetInterface` as non-built-in and non-primary. Identify the BSD `en` unit from IORegistry. The driver uses IONetworkingFamily's legacy push output and BSD ifnet/DLIL. It registers neither an `IOUserNetworkEthernet` service nor a native Skywalk packet provider.
2. **Enumerate and bring up the link.** The composite [descriptor](../../package/PianoDwc3/UsbDescriptors.h#L92) adds one CDC-NCM function with an Ethernet functional descriptor defined by CDC-ECM. Linux `f_ecm` is the comparison for raw Ethernet framing only. Piano has no ECM data path. Configuration 1 enables interrupt IN EP7 (physical 15). Data alternate 0 has no bulk endpoints. The status completion of `SET_INTERFACE` alternate 1 brings the link up and queues speed and connection notifications. Bulk EP8 OUT/IN (physical 16/17) uses 512-byte USB packets at high speed or 64-byte packets at full speed. The Mac's NCM stack exposes a separate Ethernet interface. See [endpoint state](../../package/PianoDwc3/Dwc3Gadget.h#L1102).
3. **TX, device to Mac (USB IN).** `sshd` writes to TCP over IPv6. XNU constructs a list of Ethernet output packets through IPv6/ND6/DLIL. The family calls [`outputPacket`](../../package/PianoDwc3/PianoUsbNet.cpp#L133) for each frame. The driver takes the packet-header length, copies across all mbuf fragments with `mbuf_copydata` and frees the packet on every return. On success it wakes the USB thread. Under `gNetLock`, the frame ring publishes a two-byte length and the bytes, including a two-part copy if the frame crosses the end. The USB thread polls events, services the ACM ports, then pumps NCM. [`txNext`](../../package/PianoDwc3/PianoUsbNet.cpp#L289) leaves the next frame queued when it will not fit in the NTB and zero-pads short frames to 60 bytes on TX.
4. **Submit and complete IN.** [`netPump`](../../package/PianoDwc3/Dwc3Gadget.h#L1185) takes frames only while IN is configured and free. It builds an NTB16 in a dedicated 16 KiB DMA buffer. The NTH16 is 12 bytes, followed by four-byte-aligned datagrams and a four-byte-aligned no-CRC NDP16 with a null entry. The writer caps each block at 32 frames and the negotiated IN size (2–16 KiB, rounded down for writing). A default-size NTB holds ten full Ethernet frames. The driver posts one `STARTTRANSFER`; if that block ends on a max-packet boundary below the negotiated size, the data TRB chains a zero-length TRB. The event poller dispatches the completion and [`bulkComplete`](../../package/PianoDwc3/Dwc3Gadget.h#L1267) releases the busy slot when the first TRB's HWO is clear. The Mac's USB driver receives the NTB, decapsulates Ethernet frames and passes them up to TCP and SSH.
5. **RX, Mac to device (USB OUT).** Once the software RX queue has at least 16 KiB free, `netPump` posts one 16 KiB OUT TRB. Otherwise it withholds the next request, applying USB backpressure. On completion the driver subtracts the TRB residual from the posted length, discards a standalone zero-length transfer and parses the NTB16. Accepted datagrams are queued and wake [the network thread](../../package/PianoDwc3/PianoUsbNet.cpp#L216). That thread allocates mbufs, copies bytes with `mbuf_copyback` and calls `IOEthernetInterface::inputPacket` serially. It kicks USB again after it makes room. TCP ACKs for a pull use this same RX path. See [OUT completion](../../package/PianoDwc3/Dwc3Gadget.h#L1216) and [mbuf delivery](../../package/PianoDwc3/PianoUsbNet.cpp#L154).

## How a tablet-side error reaches TCP

A free 64 KiB ring can hold 43 full frames including their two-byte record headers. A burst of 50 full frames needs 75,800 bytes. With IN busy and no concurrent drain, frame 44 through 50 are refused. A partially occupied ring has less headroom. XNU defaults `net.inet.tcp.packetchain` to 50, so the source permits such a burst even with software segmentation. A larger SSH transfer has more opportunities for this timing. A fixed application byte threshold does not follow from the queue size. [XNU TCP batching](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/bsd/netinet/tcp_output.c#L3208-L3237)

`outputPacket` returns `kIOReturnOutputDropped` (1 in the k27 build headers) after freeing a refused frame. The family installs the controller's callback directly when `createOutputQueue` returns null, and legacy `if_output` returns that callback's value. DLIL interprets 1 as `EPERM`. It can overwrite a per-frame error with a subsequent return, so the error reaches the caller when it survives processing the packet list. ND6 and IPv6 propagate it to `tcp_ip_output`/`tcp_output`. TCP handles `ENOBUFS` as congestion, whereas `EPERM` can reach `tcp_usr_send` and the writer. OpenSSH treats such a write failure as fatal. That explains a truncated pull and a possible subsequent reset. There is no direct RST call on the driver's drop path. XNU can also send an RST through `tcp_drop` after retry exhaustion or an abort. Distinguish a fatal SSH write, a TCP timeout/abort, a later reply from a closed PCB, and a peer reset by timing, TCP counters and the direction of any observed RST. [Apple callback selection](https://github.com/apple-oss-distributions/IONetworkingFamily/blob/main/IONetworkController.cpp#L885-L929) · [Apple callback return](https://github.com/apple-oss-distributions/IONetworkingFamily/blob/main/IONetworkInterface.cpp#L1394-L1425) · [XNU DLIL](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/bsd/net/dlil_output.c#L429-L472) · [IPv6 return](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/bsd/netinet6/ip6_output.c#L1544-L1593) · [ND6 return](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/bsd/netinet6/nd6.c#L4167-L4198) · [XNU TCP errors](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/bsd/netinet/tcp_output.c#L3304-L3371) · [XNU socket send](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/bsd/netinet/tcp_usrreq.c#L1183-L1193) · [OpenSSH server write](https://github.com/openssh/openssh-portable/blob/master/serverloop.c#L288-L298)

The historical branch `usb/ncm-tx1` records that vpio2's send drops increased from 0 to 7,235 across five failed 3 MB pulls. Commit `86725c02` added a family queue with stall/retry and `8827cdf5` followed up on symbol scope. Neither commit is in y12m's history. The new change uses the same queue mechanism with a default-off boot argument.

`IOBasicOutputQueue::enqueue` is the BSD-facing callback in flow-control mode. The queue owns the mbuf on `kIOReturnOutputStall`, prepends it for retry and stops output. Its enqueue callback returns success to BSD independently of the target callback's result. The USB thread requests service once half of the ring is free, and the network thread calls `service()` on the controller work loop. The family clears the stall and also invalidates a stall returned by an in-flight drain, which covers USB freeing space before the family records the stall. The driver frees mbufs on acceptance or a genuine drop and reports `kIOReturnOutputDropped` for drops. The family accounts for overflow and link-loss flushes in `queue drops`. [Apple queue implementation](https://github.com/apple-oss-distributions/IONetworkingFamily/blob/main/IOOutputQueue.cpp#L478-L734)

- **TCP on the tablet and Mac.** Run `netstat -s -p tcp` immediately before and after.
