# Results: 2026-11-19

This report records a read-only baseline audit for native macOS deployment on the Xiaomi Pad 8 Pro. It does not claim a macOS build or boot. No reboot, Fastboot transition, partition write, or device-side file creation was performed.

## Tablet

- ADB listed one authorized `piano` device: product `25091RP04C`, SoC `SM8750P`.
- HyperOS build: `OS3.0.309.0.WPYCNXM`; Android 16 / API 36; kernel `6.6.118-android15-8-gc44b714366cc-abogki519650608-4k`.
- Bootloader reports unlocked and verified boot state `orange`; Magisk `su` returned uid 0. Active slot property is `_a`.
- `/data` is 461 GiB total with 439 GiB available at the time of the query.
- All six UFS LUNs have valid primary/backup GPT header and entry-array CRCs, with matching primary/backup entry arrays. LUN 0 has 124552192 4096-byte blocks; `super` ends at LBA 3632127 and `userdata` occupies LBA 3632128 through the last usable LBA 124552186. No `linux_rootfs`, `linux_data`, or ESP is present. Slot-success/retry values remain unknown.
- The first and last 1 MiB of each of six LUNs were captured to E: and F:. All 12 pairs match in SHA-256; offline parsing verified both headers' CRCs, both partition-array CRCs, and identical primary/backup arrays. Per-file hashes, LUN sizes, and offsets are in `outputs/manifests/native-macos-27.3.json` and the two external `MANIFEST.csv` files. This is a GPT backup, not full device imaging.
- A-slot `boot_a` (100663296 bytes), `vendor_boot_a` (100663296), `init_boot_a` (8388608), and `misc` (4194304) were read-only captured on E: and F:. Each length was checked, the copies' SHA-256 hashes matched, and a fresh device reread matched the saved copy. Hashes and local paths are in `outputs/manifests/native-macos-27.3.json`. The standard boot-control structure at the checked `misc` location failed magic/CRC validation; slot-success/retry values remain unknown.
- Two temporary Fastboot sessions (no flash or other write command) reported `product=piano`, `unlocked=yes`, `current-slot=a`, `is-userspace=no`, both slots successful, retry counts 6/6, and A-slot sizes `boot_a=0x6000000`, `vendor_boot_a=0x6000000`, `init_boot_a=0x800000`. After each `fastboot reboot`, ADB confirmed the tablet on `BP2A.250605.031.A3`, slot `_a`.

## Recovery and switching evidence

The historical external backup was left untouched. Its verification log has failures for several large aggregate archives, so its integrity and applicability to 3.0.309 remain unconfirmed. Separate read-only captures of the current A-slot boot triplet and `misc` are now stored on E: and F: and verified by length and SHA-256, including a fresh device reread. They do not constitute a complete Android recovery set. The Ubuntu upstream switching source was reviewed, but no local switching operation was attempted. It does not itself validate boot success/retry state or perform post-write readback.

Follow-up recovery-package validation completed on 2026-11-19. The official Xiaomi OS3.0.309 China Fastboot package was downloaded on `mac-lan` as `/tmp/piano_images_OS3.0.309.0.WPYCNXM_20260906.0000.00_16.0_cn_d5071e52da.tgz`. The 32 Range segments each matched their expected byte length; the assembled 11,346,114,406-byte file matches the published MD5 `d5071e52da7c5dff4479d45e2775c437`, has SHA-256 `c7b0446a4704611d1d562e3b27cdd01fdd14bdee7b979973b76992c2200836e8`, and a complete tar listing read 110 entries. Read-only script inspection found `flash_all.sh` erases/flashes metadata and writes `userdata.img`; `flash_all_except_storage.sh` skips those but rewrites firmware, `super`, boot-chain, `misc` and recovery partitions, changes the active slot and reboots. Neither script was executed or qualified as safe. The archive remains unapplied and is a stock OS package, not a userdata backup; no new tablet data backup or write was performed.

Read-only storage-feasibility probe: `/proc/filesystems` lists F2FS and `/data` is mounted from `/dev/block/dm-56` as F2FS; no `/data` file contents were read. The shown mount options omit `resizable_tail_secno`. Both shell and `su` were denied access to `/sys/fs/f2fs/features`; `resize.f2fs` was not found by PATH lookup or under `/system` and `/vendor`. The exact stock kernel tree/config remains unavailable, so shrinking `userdata` is unverified and excluded from the storage design. Android common `android15-6.6` added the `resizable_tail` probe on 2026-11-05 in [`39e1749b1b88a1d9d0253e96b1d15ffed6f3fb67`](https://android.googlesource.com/kernel/common/+/39e1749b1b88a1d9d0253e96b1d15ffed6f3fb67); upstream F2FS documentation says online shrink consumes its reserved tail sections. This newer upstream work does not establish support in the tablet's stock build.

Follow-up on `F:\piano-backup\data-data\data-data.tar` found a 39-byte tar warning prefix. After skipping that prefix in memory, a read-only streaming parser read 4,719 entries totaling 169,597,666 declared payload bytes before the first tar end marker, at about 177 MB. The 52,839,244,759-byte file continues for roughly 52.6 GB after that marker and includes tar diagnostics; this unexplained tail was not scanned in full. No extraction or source-file modification occurred. The archive remains unverified and is not counted as a complete recovery copy.

## Historical deployment and present divergence

The preserved local checkout `E:\codex\2026-11-01\ni\work\piano-macos-c146` (commit `c146dfc6ce1a24c9b85df9b70003d6ecbe9fba63`, committed 2026-11-14 17:19 UTC) has dated results reporting native macOS 27.3 (`26C5035r`) desktop, GPU and input operation, Wi-Fi networking, and persistent Data on the tablet. Those reports are not evidence of current installation: today's live GPT has no native root/Data/ESP partitions. The event that returned the tablet to stock Android is unknown. The old checkout's generated `out/` assets and exact k27 tree are absent, and its tracked worktree contains edits, so neither its source changes nor its historical outputs were used.

The preserved `F:\piano-backup\data-local-tmp\tmp.tar` verifies as a 396-entry archive in its existing log. Its 13 `macos27` members include `os.img`, `data-store.img`, and `edk2-gunyah.fd`; the archived `run.sh` launches `crosvm` with the Gunyah hypervisor. These are DroidVM guest assets, not native UFS deployment images. The 2026-11-16 `fastboot -w` proposal targets 3.0.308, and its existing verification log marks several large user-data archives unrecognized. It was not executed or resumed as part of this task.

The historical checkout does not share the requested `2438556` commit object and has different `unixnu.lock` / `feeds.toml` hashes. Its reported successful install therefore does not qualify as a reproducible build of the current pinned set. A sibling historical checkout at `9097efb` contains 6.25 GB of k27/RAM outputs and four small generated inputs, but its locks differ, the exact k27 source tree is absent, and it has no persistent root/ESP image. Its verified RAM candidate is explicitly offline-only with `data-persist=0`, `same_seed=false`, and unknown installed seed source; the historical signing profile uses OS3.0.303. These artifacts remain untouched and are excluded from the current deployment set. The latest Ubuntu switch-tools release observed was v1.6.1. Its tools archive passed the published SHA-256 check, and the included `piano-switch.py` blob matched `c504b603ba1cb3629057afeb501afe5740819766`; the release targets OS3.0.303 and its installer erases Android data. The local Fastboot preflight values match this tablet, but the switch script lacks success/retry gates and readback; no switch was run. A host process inventory found two existing Windows ADB service processes and no build or VM process; no matching build, VM, or Fastboot process was found on `mac-lan`.

## Outcome

The read-only phase confirmed device identity and found a material stock-to-upstream storage-layout gap. Do not attempt a desktop boot that assumes the author's existing UFS root/Data layout. Resolve slot metadata, validate recovery assets, and prepare a concrete reviewed storage plan before any persistent storage or boot changes.
