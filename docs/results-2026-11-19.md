# Results — 2026-11-19

The Bluetooth panic-text channel captured a natural reset during BlueTool initialization:
`Invalid/destroyed mutex` at `lock_mtx.c:141`. The frozen collection places the mutex in PianoBluetooth; decoding the
address loads in `qbt_transport_init` identifies `bt_tty_lock`. Its type was zero instead of `LCK_TYPE_MUTEX` (0x22).
The owner state was a compressed thread ID, not the destroyed-lock marker. Kernel startup declarations had left the
kext's lock and group uninitialized; uncontended acquisition can succeed until contention checks the missing type.

The transport now allocates its group and initializes the mutex before publishing any sysctl or character device.
An atomic initialization claim rejects repeated starts and permits retry after group allocation failure. The lock
remains allocated while the existing device and worker callbacks can use it. The prior panic-text kernel and hold
are retained. Native object compilation confirms runtime initialization imports and no lock STARTUP records.
The fix awaits six tablet boots with complete daemon, serial, HCI and framework exposure; it is not yet a stability pass.
