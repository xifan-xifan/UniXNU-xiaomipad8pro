## Fastboot boot source review

The source lineage is now pinned to Qualcomm CodeLinaro repository `clo/la/abl/tianocore/edk2`, tag `KERNEL.PLATFORM.3.0.r23-02400-kernel.0`, commit `aef4e86045bd151a54d33bab8ae5e8e62462a8f4`. OpenABL's pinned fetch script identifies this URL, tag and commit. CodeLinaro API file contents at that commit match the Mac reference files byte-for-byte by SHA-256: `FastbootCmds.c` (128,682 bytes, `a1b53035b3c89c85c5f1f13dde891b5a3e1858cc073311fd5e58649742ae6656`), `BootLinux.c` (89,499 bytes, `2b578b0344d7c67fcc1126d3a9453ebb2d59f8a0214721c9a5f87aef06f07a01`), and `PartitionTableUpdate.c` (68,045 bytes, `2f089ea344d20ceb1db7e2ac8cb83b96f2656b25f5a376f6bfab10f9928fa58a`). This proves the reviewed source revision, not that Xiaomi built its distributed ABL from it.

OpenABL `main` was rechecked through GitHub API at `2227e24341cae531e1d7e9f3cd710920545879e8` (committer date 2026-11-19). Its pinned Qualcomm tree adds `Abl/openabl.patch`. That patch changes `BootLinux.c` boot-stat timing/kernel cache handling and Fastboot's published bootloader-version variable; it does not change `CmdBoot` or `PartitionTableUpdate.c`. Therefore its GPT source review is unchanged, while its `BootLinux.c` behavior must be treated as OpenABL-patched only where explicitly noted. The patch is a separate project delta, not evidence about Xiaomi's build configuration.

In that source, unlocked `CmdBoot` sets the boot-device-image flag, calls `ClearUnbootable()` for multi-slot boot, passes the downloaded boot image to `LoadImageAndAuth()`, then clears the flag before calling `BootLinux()`. `ClearUnbootable()` clears the active boot partition's unbootable attribute in the in-memory GPT. `UpdatePartitionAttributes()` compares that in-memory table with its saved copy and returns without block writes when unchanged. If changed, it updates the primary and backup GPT through `BlockIo->WriteBlocks()` and flushes. The previously captured A-slot state was successful=1 and unbootable=0, so this specific operation would not alter GPT if that state remains unchanged and this code matches the binary. This does not establish that other boot paths have no writes.

`FindBootableSlot()` in the reviewed source does not decrement retries for a successful slot. Its unsuccessful-slot retry decrement is gated by `!IsBootDevImage()`, but `CmdBoot` clears that flag before entering `BootLinux()`. The call path and the device binary's exact implementation therefore still require confirmation; no general claim that temporary boot cannot change A/B state is made.

The reviewed `BootLinux.c` selects an `init_boot` ramdisk only when `Info->HasBootInitRamdisk` is true and the boot header is version 4 or later. The planned Android boot v2 container does not meet that source condition and appears to use the downloaded image's ramdisk. The reviewed `VerifiedBoot.c` takes the header version from the preloaded image when present. The device binary and its populated `BootInfo` still require verification.

The reference source conditionally writes the non-volatile UEFI variable `DestinationCore` when `TARGET_LINUX_BOOT_CPU_ID` enables CPU selection. In the pinned source, `BootStatsSetTimeStamp()` reads timer/shared-memory variables and writes the timestamp through a memory-mapped shared-IMEM address; this code path does not call block I/O. Whether the shared-memory region retains values across reset is not established. The target build configuration has not been matched to this ABL. Other UEFI/blackbox log backends, error handling, and hard-reset persistence paths remain unaudited. The decompressed binary strings alone cannot rule these out.

The reference AVB2 path can request a TrustZone rollback version update before image verification when its policy allows it. A separate path can update a rollback index when verification reaches the update branch and the new index exceeds the stored value. `avb_ops.c` gates that write on rollback policy, and `DeviceInfo.c` passes the updated device configuration to `ReadWriteDeviceInfo(WRITE_CONFIG, ...)`. In the same reference revision, `QcomModulePkg/Library/BootLib/LinuxLoaderLib.c` implements `ReadWriteDeviceInfo()` by locating the Qualcomm Verified Boot protocol and forwarding the operation to `VBRwDeviceState()`. The final storage backend depends on the firmware that implements this protocol. Device-specific rollback policy and the Xiaomi protocol backend remain unverified.

Result: no temporary boot was attempted. The exact source lineage is established for the Qualcomm reference tree, but Xiaomi source-to-binary build provenance, build configuration, and remaining non-GPT persistence paths are open. This is not sufficient to assert that the distributed binary has no persistent writes or to pass the authorized temporary-boot gate.
