# ufs193: rebuilt KC boots past IOKit into bsd_init (2026-11-24)

The 147 MB kernelcache is reproducible again. `kc-base.kc` already carries the
26 native kexts, so rebuilding over it needs the bundles supplied through
`--native` to *replace* their copies instead of being appended: the naive
rebuild hit `no room for a 0x430d0-byte native kext __DATA` after the base's
own 26 kexts were kept. The replace variant is
`patches/k27-kc/0002-kc-build-replace-native-kexts-in-the-base.patch`
(`keep -= {spec['bundle'] for spec in natives}`, and stand-in rebinding skips
names the base no longer has). With it the rebuilt KC is 0x8c48000 bytes, the
same size as `piano-ufs184.kc`, and every native kext lands at its ufs184
address (NativeUfs __TEXT `0xfffffff007095190`, __TEXT_EXEC
`0xfffffff008b4aea0`, __DATA `0xfffffff00cb08460`).

## The corecrypto step was still missing

`piano-ufs191.kc` (SHA-256 `26beb9b8dd972df9dd93685ecb6e0d056c3f915e03a4d27bbfdf643570704e63`,
image `e2e15b1e...`) and the control `piano-ufs192.kc` (`bcd52632...`, image
`73d5c107...`, built with the pre-sync `desc-ufs184-nostand.json` object) both
returned to fastboot after 67.1 s with the console stopping at
`kernel_bootstrap: PE_init_iokit`. ufs192 rules out the synchronous
`registerService` change as the cause: the identical object set that booted
inside ufs184 fails the same way when relinked.

Comparing `com.apple.kec.corecrypto` between the KCs found the difference:
ufs184 carries `_corecrypto_kext_start` as `mov w0, #0; ret`
(`00008052c0035fd6`) where the base and the rebuild carry Apple's original
`5f2403d57f2303d5`. The rebuild path lost the corecrypto patch that earlier
images applied after building. Re-applying it to ufs191 gives
`piano-ufs193.kc` (SHA-256
`1bf26bbaa01009ac86ab227f9b673bdc5998ec3332e966e3d8a0630cee8f66b6`, image
`boot-piano-ufs193cfg.img` `78219992fc6af9d61b22890a5ff89f567696f4974f9775af0a59b9d2d2abe0a1`).

## Device result

ufs193 ran under `fastboot boot` only and returned to fastboot after 85.1 s
(ufs184: 84.7 s; the unpatched builds: ~67 s), then `reader.img` captured the
console. The capture contains 318 `NativeUfs` lines: the whole media chain
(`IOMedia -> NativeUfsBlock -> NativeUfs -> K114cAP -> Root -> (none)`), the OS
media registering under `OS media register entering (synchronous)`, swcrypto
threadpool init, and `dev_init:299` finishing the OS container (block size 512,
28307456 blocks). The console also shows `bsd_init: calling ...` with the
`sd_init:` calls, i.e. the kernel is past `PE_init_iokit` and inside BSD
initialization. No `launchd`, no GPU/userland, no desktop.

The console text is bit-corrupted in the capture (both ufs184 and ufs193 dumps
show the same character noise), so quotes above are reconstructed from
nearby runs; the run timings and the presence/absence of `NativeUfs` lines are
the reliable signals.

Every run returned to HyperOS OS3.0.309.0.WPYCNXM with `boot_completed=1` on
its own; no partition, GPT or userdata write.

## Next

Read the tail around `dev_init:299` to see whether the OS container's
matching thread finished or is parked, then drive the root publisher that
follows it. `boot-piano-ufs193cfg.img` is the current baseline for any further
NativeUfs change: rebuild it with the replace builder and re-apply the
corecrypto patch every time.
