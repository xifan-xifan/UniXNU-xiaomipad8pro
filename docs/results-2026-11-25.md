## Safari video decode

- H.264 1080p plays on the Iris hardware decoder in Safari on the installed system: 600 frames, 0 dropped.
- 4K: an early run showed HEVC 2160p at 3.6 fps. That was a test harness bug: Safari restored a previous run's tab, and the
  checker accepted that tab's stale result while the real tab was hidden and paused. With the fixed checker on the installed
  system: HEVC 2160p 600/0 at 29.9 fps and H.264 2160p 591 decoded / 5 dropped, both in Apple's software decoders. That is by
  design: the hardware path covers H.264 up to 1920x1088. H.264 and HEVC 1080p are 600/0. VP9 and AV1 do not play.

## Login-window idle CPU

At the login window the system kept about 1.3 cores busy. Samples showed the audio daemon retrying a Bluetooth audio routing
start that needs a logged-in user, and each retry queried the configuration daemon. The fix holds that daemon at the login window
and resumes it at the login. Installed in v13.1y12j. Auto-login was not chosen.

## Chrome GPU findings

- Chrome runs on the installed system on software rendering. On RAM boots Chrome resets the tablet shortly after it starts. The inferred
  cause is that its download and launch fill the RAM-backed Data disk. A larger volatile disk keeps the RAM image from booting, so
  Chrome is tested on installed boots only.
- With kernel 0074 and the App view layout (v13.1y12k), our Metal plug-in now loads inside Chrome's sandboxed GPU process. It then
  refuses to open, because Chrome's GPU sandbox allows no writable shader cache directory except Apple's names. Plug-in frontend
  0012 opens without a disk cache when none is writable. It is built for the next daily.
- WebGPU in Chrome fails at random when it allocates transfer buffers. Chrome's V8 sandbox reserves about 1 TiB, but our user
  address space ends at 512 GiB. The sandbox is then only partly reserved (confirmed on v13.1y12k: reservation 128 GiB, a mapping
  probe 145 of 200). The fix is a 47-bit user address space, a kernel change now being implemented with its own analysis first.

## Core Image and the 4 GiB GPU windows (RAM)

Two Core Image paths on 4032-pixel images ran out of memory on every installed build since v13.1y12d. The confirmed root cause is
the 1 GiB ordinary GPU window per client. The `slots2` change gives 64 client windows of 4 GiB in a 256 GiB aperture (1 GiB per
object, off switch `piano-gpu-va=64`). On RAM (slots2-qual1): 30 of 30 graded Metal image paths pass, including both 4032 Core
Image paths and the 4032 HEIC MetalKit texture, with no GPU page fault and nothing refused. Safari WebGL 2, WebGPU and H.264 1080p
(0 dropped) also passed on the same boot. The one FAIL was a system performance diagnostic report, not a crash, so it is a test
issue. This change goes into the next daily.
