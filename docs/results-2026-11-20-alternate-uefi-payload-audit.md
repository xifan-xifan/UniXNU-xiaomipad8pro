It is an iPadOS 17.7.11 / 21H461 port, separate from the locked macOS 27.3 profile. Its README says experimental and not yet XNU-booted. No source or binary from it was imported into the current build.

The repository's dated device reports show real-device `fastboot boot`, `fastboot stage` (160 MiB), and `fastboot oem ramdisk` succeeding to publish a FAT payload volume. The UEFI menu rendered and volume keys/power were reported working. This is useful hardware evidence for a RAM-resident staged payload transport, not evidence of a successful XNU boot. The payload is not an Android boot ramdisk: the host sends it after UEFI re-enumerates Fastboot, avoiding the vendor ABL's boot-image ramdisk ceiling.

The same reports document subsequent XNU handoff failures: first FAT32 large-file reads returned `EFI_VOLUME_CORRUPTED`, then FAT16 exposed `EFI_UNSUPPORTED` because DarwinBoot expected EL1 while the Mu-Silicium path remained at EL2. The branch contains proposed FAT and EL1 transition patches, but the checked main README still reports no XNU boot and the reports do not establish a successful post-patch XNU handoff. Separate progress records across commits must not be combined into a claim of one successful end-to-end run.

The public `piano-fastboot-payload.patch` raises the experimental branch's UEFI `FB_MAX_DOWNLOAD` from 64 MiB to 256 MiB and implements stage/publish in its own `pianoPkg`. The current lock pins `piano-uefi` at `31545f9392d5f5c2acae14cec2fa3a0aa1de51d4`, whose `PianoFastboot.c` retains `FB_MAX_DOWNLOAD SIZE_64MB`. This establishes a concrete adaptation requirement if the matched macOS payload exceeds that limit; merely enlarging the Android ramdisk or copying the patch without porting and review is not sufficient. A smaller payload that fits the current cap remains an alternative to investigate after the exact candidate is restored.
