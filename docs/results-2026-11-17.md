# Tablet results, 2026-11-17

RAM boots (`fastboot boot`) of macOS 27.3 with a volatile Data disk. "Confirmed" means a tablet log, a CoreAudio/CoreWLAN read-back or a
webcam recording shows it. Every change below was preceded by a written analysis of the whole path (Apple binaries, our driver, the
reference ports); runs that only found a harness problem are not counted as results.

## Wi-Fi: joining through macOS works (confirmed)

- Run wifi-join9b: `networksetup` -> airportd -> IO80211's `Apple80211Associate2` -> our Apple80211 user client (SET 20) -> association
  (WPA2 Personal, -40 dBm, 5 GHz) -> the four-way handshake by our supplicant -> authorized port, link up -> DHCP (private IPv4 after
  4 s) -> gateway ping 3/3 -> public DNS. No panic.
- The gates found on the way, each fixed once: the scan-done event (10, not 11 = country changed), the TKIP group-cipher capability bit
  Associate2 checks, the 656-byte request delivered inline in the user-client buffer, its upper-auth word 0x08 (WPA2-PSK), the menu
  profile handed to the join engine, the 540-byte association-done event, and a supplicant in the test image that accepts a profile
  from the system (the test recipe now stages the current userland).
- The country code reads nil for ordinary processes because macOS withholds it without location permission (a privacy filter, not a
  driver answer).

## Sound: the speakers play at the system volume (confirmed)

- Run aud-drop1: one continuous ~3 s tone per recording at -35.6 / -21.2 / -15.5 dBFS for volume 25 / 60 / 100; mute silences; the
  volume keys and `osascript` follow; CoreAudio's own read-back of the volume control is finite and equal to the set value.
- Root causes found on the way: the IOAudio2 control's range map is an array of range dictionaries and its dB fields are signed 32.32
  fixed values (a NaN volume silenced every sample before); the HAL ring geometry must not change after the HAL attaches; the
  amplifier status reads must not delay the DSP refill. About 11 short underruns remain per tone; they are not audible in the
  recordings.

## Hardware video decode: one kernel frame decodes (confirmed)

- Run vid-v2c5: three complete power cycles with the firmware loaded, authenticated and shut down cleanly; a stale CPU NoC low-power
  request is withdrawn after its timeout (it had reset the SoC on the third power-up).
- Run vid-v3b: the firmware boots and answers the host interface: version `vfw-3.5 rel0039`, handshake 8.8 ms, the command/message
  queues work, power collapse and resume 10 of 10 times, no SMMU fault.
- Run vid-v4a: the kernel's own 320×240 AVC AU decodes to the exact active NV12 golden hash; DRAIN/CLOSE and DMA teardown pass.
- Run vid-v5a: Apple's VideoToolbox selects our native PV decoder, opens its user client and sends dsta. The driver replies
  -12910 before any input. The decoded 27.3 serializer and the exact tool format reproduce the cause on the host: a legal
  four-byte QuickTime extension terminator failed our strict atom check. V5b accepts only that terminal representation,
  retains the exact AVC restrictions, and logs dsta/dcan decisions.
- Run vid-v5b: hardware/PV session creation and all format queries pass. The first malformed sample reaches the kernel and
  is rejected before DMA, but its missing error completion leaves the tool waiting; the valid AU is never submitted.
  Decoded 27.3 control flow confirms that a codec error reply alone does not emit a frame, and that the public wait invokes
  finish. V5c adds worker-owned rejected-frame completion and preserves an empty session across finish. Full VT output
  remains unconfirmed; the firmware and Iris transaction are unchanged.

## Boot windows

- Run vid-bootwin5 (night): Installer Progress acquires the cinematic boot windows once the display offers a mode-sized surface as the
  displayed one; the window is a still copy of the boot frame, so no video decode is needed for it.

## Sensors: automatic brightness still blocked (confirmed)

- Run sens-ab1 completed discovery and attributes for all six sensor types, but the light client's enable and subsequent cleanup
  requests received no answers; six timeouts stopped the guard with no samples. Manual backlight control remained available.
- The failure also affected charging communication: GLINK receive and doorbell counters stopped advancing, and MCA timeouts grew
  from 22 to 82 between 60 and 120 seconds. The unchanged fatal bit and charger generation did not establish a healthy transport.
  The earlier s1c first-sample runs continued receiving and had no MCA timeouts. Automatic brightness has not passed on this image.
