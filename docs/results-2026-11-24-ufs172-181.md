# ufs172-181: media 发布与匹配调度

日期: 2026-11-24

范围: 仅 `fastboot boot` 临时镜像。每轮由 `tooling/native/run-ufs17Ntr.ps1` 自动启动、
抓串口与 panic 区、再回到已完成启动的 HyperOS OS3.0.309.0.WPYCNXM A（`boot_completed=1`）。
未写分区、GPT、boot 镜像或 userdata。

## 结论

- ufs172/174: OS 窗口到达 APFS 之前停在 `AMFI: developer mode is force enabled`，
  日志稳定，无 panic。ufs173: 轮询/喂狗运行到 240 s，被 `piano-reset-after` 正常复位；
  说明内核调度本身可用，慢的是根卷匹配。
- ufs175: 去掉独立 ping 线程，把心跳内联到回调与读路径；日志与 ufs172 同点。
- ufs176: 加窗口首块字节 dump。**OS 窗口第 0 块就是 APFS 容器超级块**
  `f99c9657 9b2eddaf 01000000 00000000`，不是 GPT；因此让分区方案探测这条路线不成立。
- ufs177: 去掉 `device-type=Generic`（阻止 IOBlockStorageDriver 抢匹配），在 `start()`
  内发布 IOMedia 后同步 `startMatching`。结果 **APFS 真正接上**：
  `swcrypto_threadpool_init`、`dev_init ... block size 512 block count 5697536`（SystemOS
  块数）出现；但 OS 窗口的同步匹配把发布线程卡死，OS 媒体虽在 ufs178 才发布成功。
- ufs178: OS 窗口改用异步注册。媒体发布成功（`A7672058-...`，14.49 GB），父链
  `NativeUfsBlock -> NativeUfs -> K114cAP -> Root` 正确，但 `matched drivers 0`，
  5 s 一次的 child probe 全部 `busy=1 matched=0`。
- ufs179: 为媒体单独起 `kernel_thread_start` 做 `startMatching`。**线程创建成功但
  85 s 内从未进入函数体**（无 `media match thread entering`）。
- ufs180: 增加线程启动确认日志 `media match thread started 0x...`。确认线程对象已
  创建，但同一时段内线程体仍不执行；同时 APFS 没有匹配到任何窗口。
- ufs181: 回到“先发布两个窗口，再由发布线程同步驱动匹配”的顺序（`publishedMedia`
  保存节点，发布线程在 monitor 循环后逐个 `startMatching`）。日志在 `monitor 0`
  之后完全停止，与 ufs178/179 同点；即发布线程在第二个 1 s tick 前就再没有任何
  IOLog 输出，`fastboot` 于 84.6 s 恢复。

## 关键观察

- 早期 IOKit 阶段（IOBSD 资源出现后、`mac101 initbsd` 之前）`kernel_thread_start`
  返回 `KERN_SUCCESS` 但派生线程得不到 CPU；ufs177 中同样的机制在 BSD 起来后
  （`mac101`/`gop` 线程）能正常运行。
- ufs177 的载荷已经能驱动 APFS 挂 SystemOS 容器；后续 ufs178-181 反而在媒体
  匹配调度上退步，把问题收敛到“谁、在什么时候调用 `startMatching`”。
- 所有轮次都没有真实块读取日志（`NativeUfs: ... read block`），说明 APFS 在
  IOMedia 之后没有发出读请求；卡点位于 IOKit 匹配/打开阶段，而非 UFS 传输。
