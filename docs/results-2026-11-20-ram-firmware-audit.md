# RAM boot firmware audit (2026-11-20)

The pinned piano-uefi revision `31545f9392d5f5c2acae14cec2fa3a0aa1de51d4` lists UFSDxe, EnhancedFatDxe, VariableRuntimeDxe and BdsDxe in `uefi/pianoPkg/Include/DXE.inc` and `APRIORI.inc`. The lists establish which components are declared. They do not identify the variable store backing or prove which block operations the final composed firmware performs.

The device repository's `firmware/patches/unixnu/0001-UniXNULib-config-prefer-the-RAM-payload.patch` tries the launching volume first, then prefers the RAM payload in filesystem enumeration. If neither supplies a configuration and no configuration error stops the search, it can still try other filesystems, including UFS. The preference does not enforce RAM-only boot. The XNU `data-persist` setting cannot constrain earlier firmware execution.

Qualification requires auditing the final FD's active variable services and UFS behavior, and ensuring a diagnostic image stops when the RAM configuration is absent rather than loading a configuration from disk. This review was based on source at the pinned revisions. The final FD and physical device were not exercised.

The retained 3,145,728-byte `piano-uefi-A-bundled.fd` hashes to `394c5c786f4d114ccb0e709083ce574e4c5964593bd656bdffe8dd0f2e5bd5d2`. The historical `ram-native-base-control/build-A-bundled.json` records that digest and classifies the build as `OFFLINE_CANDIDATE_NOT_DEVICE_TESTED`. The digest differs from both FD A entries in the current artifact catalog. Keep the retained FD as an offline comparison sample pending a source-to-artifact provenance match. A check under the Mac checkout and `/tmp` found no standalone `.fd` file.

The pinned board DXE lists select the source `VariableRuntimeDxe`. The same repository carries a separate Qualcomm `VariableDxe` binary. The presence of that binary in the repository does not establish its inclusion in the composed FD. Resolve the includes and inspect the firmware volume before drawing conclusions about persistence.

The retained FD's outer firmware volume contains a GUID-defined LZMA section. A read-only Python decode yielded 8,097,800 bytes. UTF-16LE name checks found VariableRuntimeDxe, UFSDxe, BdsDxe and UniXNURamDiskDxe. The same scan found no exact VariableDxe, FaultTolerantWriteDxe or FvbServicesRuntimeDxe name. These are string observations from the historical sample. Variable-store backing still requires protocol and configuration evidence from the deployment FD.

The pinned DSC include chain runs from piano.dsc through PakalaPkg and QcomPkg to SiliciumPkg.dsc.inc at Mu-Silicium e51cd877. SiliciumPkg sets PcdEmuVariableNvModeEnable to TRUE. In Mu Basecore cfb93724, VariableNonVolatile.c selects the emulated store with that setting, backed by a runtime pool or a reserved memory address, and VariableDxe.c skips registration for the fault-tolerant-write notification. This resolves the source-level backend for the declared variable driver. The composed deployment FD settings and other firmware storage paths still require validation.

No device boot or full RAM image was tested.

The retained successful FD's decompressed firmware volume contains the entire generated VariableRuntimeDxe PE32 section (46,596 bytes), matched byte for byte at offset 427,216. The generated driver settings show emulation enabled and a zero reserved-store address. This is static build evidence. Other UFS paths and actual tablet behavior remain unqualified.

The staged UniXNU core also has a separate fallback path after configuration discovery. `Main.c` calls `UniXNUConnectAll()` before `UniXNUConfigLoad()`. If no configuration is loaded, `Config.c` parses the built-in configuration and calls `AddFallbackLoaders()`, which probes every SimpleFileSystem handle for a fallback EFI loader. Restricting `TryVolume()` alone leaves this second discovery path and the earlier controller connection active. A diagnostic profile needs to constrain both discovery paths and qualify firmware storage behavior before use on the tablet.

Byte comparisons against the successful FD also matched the complete packaged PE32 sections for UFSDxe, PartitionDxe, Fat, BdsDxe and CapsuleRuntimeDxe. This confirms the storage and boot-manager components are present in the audited artifact. Execution and write behavior remain unverified.

The UEFI-only image was assembled with the pinned BootShim, verified mkbootimg script, retained boot DTB and independently built FD. The WSL result is under `/tmp/piano-fd-device.tRBw3k/out/uefi-only.jxAF2v`. Offline checks matched the embedded FD and DTB bytes, header ID and image SHA-256. The full verifier requires the Ubuntu v1.1.0 maintenance reference image, which was absent from the staging and searched historical directories. Firmware storage isolation and device boot remain unverified.
