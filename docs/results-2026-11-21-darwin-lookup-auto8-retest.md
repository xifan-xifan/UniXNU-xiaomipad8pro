# Automatic eight-core probe with prearmed capture

After the first probe, ADB verified HyperOS `OS3.0.309.0.WPYCNXM` on `_a`, `sys.boot_completed=1`, and Android marker SHA-256 `306a063b9b6d71bb48419efc7cf512c95c789d493a73d178e481a57dc82575f3`. The reset mechanism was not observed.

Before the second RAM boot, ABL again reported slot A successful and bootable with six retries and no snapshot update. The prearmed Windows capture reached `piano-uefi` and `oem log` returned OKAY in 90 ms. The capture script incorrectly treated the subprocess status as failure and skipped `get_staged`. The script now checks the reported OKAY and requires a nonempty output file after download. The manual retry missed the interface. Firmware log contents, XNU handoff, and the second Android return remain pending.

On a third run, the corrected prearmed capture downloaded a 128-byte firmware log from piano-uefi. It contains astboot: ready as piano-uefi, BDS console ready, DarwinBoot protocol present, and starting menu, but no UniXNU menu or XNU handoff line. The image then left USB; neither ADB nor Fastboot was available at the immediate host check. This proves the driver protocol is present in the tested build but not that DarwinBoot accepts or loads the payload. The capture script's first two failures were host-side stream/status parsing: Fastboot oem log writes OKAY to stderr, while get_staged writes Uploading ... OKAY to stderr despite an empty stdout file. The script now recognizes both formats, but a successful run through the corrected get_staged path still needs direct execution against the next UEFI window.

ADB later verified the second run returned to HyperOS on slot A, boot completed, with the same marker digest. The third run's 128-byte firmware log matches the action-only lookup log byte for byte (SHA-256 96adbe6d180034538666ff4413f6d0284d117d01ae512e863652b5e2c61e45c2). Both captured Fastboot success lines match the updated local watcher's patterns. A later capture needs to sample near the automatic selection to observe loader dispatch.

Before the fourth run, ADB verified HyperOS on slot A with boot completed and the same marker digest after the third run. The fourth run downloaded the same 128-byte early log. The watcher stopped after that download because Get-FileHash was unavailable in the capture subprocess. The local watcher now prints the sample path and leaves hashing to the parent shell, allowing the scheduled 3.5-second and 6.5-second samples to run. The fourth Android return remains pending.
