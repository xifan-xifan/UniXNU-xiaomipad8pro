## Data mount, launchd and the mode switch

- **Launch and privilege.** The system LaunchDaemon uses absolute program paths, a root-owned plist and script, and a system command search path. It runs as root. The mode OID has no `CTLFLAG_ANYBODY`. The test-only `PIANO_DC_*` overrides are absent from the plist. Its install and system launch environment, the executable's parent directories and `/private/var/run` must remain under trusted control. `RunAtLoad=true` runs once each time the job is loaded. Boolean `KeepAlive=false` creates no restart condition, including after failure or a signal. An explicit bootstrap or kickstart can run it again. No mount-triggered or crash-triggered loop exists. [Apple launchd plist semantics](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5#L170-L223) · [Apple XNU sysctl implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sysctl.c)
- **Slow boot and state.** The job polls for up to 180 s of sleep while mount commands run. It exits cleanly if Data never mounts within that budget, the mode OID is missing after the mount, or the store is blank, fresh, failed, degraded, read-only, kept, or unreported. A kernel without the live state field stays serial when armed in mode 2. A second invocation observes mode 1 and skips the write. Two concurrent invocations can both observe 0, but their fenced writes serialize and an unchanged mode does not reset the counters again. A manual rollback can be promoted by a later explicit restart of the job with the key still enabled.
- **Mount race scope.** The second APFS mount sample catches an observed unmount, and the writer fences and rechecks kernel store health. The samples do not pin a VFS mount or prove the mount source is the NativeRamBlock-backed APFS volume. An administrator who replaces or force-unmounts Data between the final sample and the sysctl can therefore get a mode change without that mount. The sysctl itself switches the disk instance and keeps its I/O safe. If a future recovery profile can substitute Data at that path, bind the check to the intended volume and its mount lifetime in the kernel before enabling this job there.
- **Interrupted job.** A userland stop before the write leaves serial. A stop once the kernel enters the fenced handler can leave either whole mode depending on how far the handler got. There is no persistent mode flag or on-disk format transition. The next mode read is authoritative. The status is a last complete report, can lag the mode or be absent, and is never consumed as a gate. A stop between a successful kernel write and the status rename can leave the prior report. A reboot with `data-store-concurrent=2` starts serial again.
- **Drain and ordering under load.** In serial, `serveExperiment` holds the disk gate through all device calls, bitmap publication and accounting. On 0→1 the writer acquires that gate before fencing, so the serial I/O has finished even though the parallel inflight count was zero. With parallel I/O the fence closes admission and waits for all active stages to return. The return comes after DMA completion or quarantine, range release, and any bitmap FUA. Completion callbacks are issued outside the gate and can still be pending across the fence. New overlapping writes and reads are serialized by whole 4 KiB page range, including partial-sector RMW. Disjoint ranges may complete out of order. The mode switch serializes with suspend/resume fences and honors the held state. It requires healthy transport progress to acquire the gate and drain. [Mode handler and storage I/O](../../package/NativeRamBlock/NativeRamBlock.cpp#L677) · [Admission and fences](../../package/NativeRamBlock/ConcurrentDirect.h#L33)
- **FUA and barrier scope.** Both modes send every data and bitmap write via tracked UFS writes with FUA. A new bitmap bit is written after its data is durable. Parallel publication can combine already-durable disjoint runs. Synchronize and synchronize-cache use the same fence, so a synchronize that races a mode change still drains prior admitted work. Neither fence promises FIFO relative to a previous caller that has yet to acquire admission, or waits for upper-layer completion delivery. NativeRamBlock does not advertise the separate IOStorage Barrier feature. Its synchronize override treats any option and range as a whole-device drain. The mode handoff preserves the write-through path's existing power-loss ordering for acknowledged data. It does not turn a multi-block request into an atomic on-disk transaction. [Direct disk write order](../../package/NativeRamBlock/DirectDisk.h) · [Bitmap publication](../../package/NativeRamBlock/ConcurrentDirect.h#L124) · [UFS tracked FUA](../../package/NativeUfs/NativeUfs.cpp#L1814) · [Apple IOStorage feature contract](https://github.com/apple-oss-distributions/IOStorageFamily/blob/main/IOStorage.h#L52-L85)

## Daily PianoUsbNet TX flow

- **A host that stops reading.** One NCM IN remains outstanding, then the 64 KiB TX ring fills. The target returns the family retry/stall status without freeing the head mbuf. Under a sustained stall, new single-packet enqueues hit the current input list's capacity and get dropped. Intermittent drain presents the separate backlog risk above. Ordinary stalls do not cause a retry spin or a controller reset. When IN drains and the ring becomes half free, the network thread asks for asynchronous service. Apple's public implementation uses a service counter to handle a wake arriving before the callback has returned its stall. A silent endpoint that never completes and never produces a link/reset event can keep NCM TX stalled indefinitely. The local EP0 watchdog will not diagnose an isolated bulk-IN wait. A future NCM-only progress diagnostic can distinguish that condition from idle host backpressure before considering recovery. [TX path](../../package/PianoDwc3/PianoUsbNet.cpp#L188) · [NCM pump and watchdog](../../package/PianoDwc3/Dwc3Gadget.h#L292) · [Apple retry and service](https://github.com/apple-oss-distributions/IONetworkingFamily/blob/main/IOOutputQueue.cpp#L366-L595)
- **Link down and suspend.** Alternate 0, bus reset, detach and unconfigure end the session. The gadget reports carrier down, the rings clear, and the network thread stops and flushes the family queue before reopening it. A down/up pair before the thread runs still leaves a reset pending. On configured-host sleep with USB kept, pending IN and the TX stall survive. Wake resumes polling and completion either consumes the IN and reopens space, or disconnect/reset drops the backlog. The soft-disconnect sleep case clears the link and enumerates anew. The USB power-off callback waits for the USB thread with a 500 ms deadline. It does not wait for the family queue to drain. [Link and queue reset](../../package/PianoDwc3/PianoUsbNet.cpp#L176) · [Gadget link state](../../package/PianoDwc3/Dwc3Gadget.h#L1130) · [USB PM path](../../package/PianoDwc3/PianoDwc3.cpp#L2898)
- **RX, shell and system progress.** The gadget services ACM ports first and considers NCM OUT before checking whether IN is busy. Family restart drains asynchronously, so a sustained TX drain does not take the RX thread. Link-down flush still calls family `stop()` synchronously. The published implementation can wait for a running or scheduled dequeue. The driver calls it with the byte-ring lock released, closes new enqueue capacity first, and the TX callback has no USB or work-loop wait, so no host-dependent lock cycle is visible. If RX falls behind, the gadget withholds the next OUT when its ring lacks one NTB of headroom. A real endpoint-command timeout can invoke the existing whole-controller recovery and interrupt the ACM debug shell. A host-wide USB wedge can take both transports out on the host side. A full NCM TX ring by itself leaves the independent ACM port able to progress. [ACM pump order](../../package/PianoDwc3/Dwc3Gadget.h#L262) · [NCM OUT and IN](../../package/PianoDwc3/Dwc3Gadget.h#L1185) · [Apple queue stop](https://github.com/apple-oss-distributions/IONetworkingFamily/blob/main/IOOutputQueue.cpp#L521-L551)

## M5 wake and display power

With the timing engines stopped, the wake sequence validates the retained bonded route and DSI parameters. It disables the hosts, forces the reset clocks and pulses both host reset registers. It restores clock settings, enters command-only mode on both links, issues DCS `11`, waits 120 ms, then issues `29`. It restores video controls and the bonded CTL route and starts timing after the DCS sequence. The DCS path limits busy and DMA-done polls to 20 ms and 50 ms respectively. A failed command with partial stores gets a reset attempt before restoring its FIFO/DMA words and restarting video. The running-engine variant keeps its front-porch gate. This follows the repository's pinned Ubuntu trace for the ordering of command-capable hosts, panel wake and video startup. The native retained-controller path skips the Linux full PHY/panel power cycle. [M5 reference analysis](../drivers/dpu-m5-analysis.md) · [Wake sequence](../../package/PianoDpu/DpuPanel.h#L652)

The framebuffer's gated power hook records the desired state and queues its worker. The worker drops the copy lock before calling DPU. Backlight blank acknowledgement and optional touch park have separate 800 ms and 600 ms deadlines. With the reply fix, the DPU caller waits at most one 1.5 s deadline on either edge, assuming the scheduler and request lock can run. On failed wake or lost reply, the copy worker releases software presentation and the framebuffer work loop handles backlight publication, subject to any superseding power edge. The fallback can progress without another physical transition or a system reset. A timed-out off that later succeeds has one best-effort asynchronous hardware undo on the DPU worker. These are software wait bounds. A permanent black screen or a hardware bus stall remains outside their guarantee.
