# Apple APFS boot phase audit (2026-11-22)

The Mac attached the retained 26C5035r OS image read-only and inspected the Apple `mount` binary with SHA-256 `0d6429c5017fd96818795c9ffe74c011b3e9e8f2871496a6319e97db664f8126`. Its strings identify phase argument validation, the absolute path `/System/Library/Filesystems/apfs.fs/Contents/Resources/apfs_boot_util`, a non-APFS skip branch, and an exec failure message. The arm64e slice imports `execv`. These are static observations. The exact branch conditions and argv remain to be traced.

The bundled `apfs_boot_util` hashes to `60955567a4d5f82bb953cc391fd2ecd471d76e910c0cb4e5e70fed30a76b8931`. Its phase strings describe role-volume lookup and optional VM volume creation in phase one, and Data lookup against the root device, root mount upgrade and media key migration in phase two. The arm64e slice imports APFS volume creation, role lookup, volume group stitching and media key migration, as well as mount and unmount. A generic passthrough to the stock phase helper therefore needs proof of branch selection and write boundaries on the native split-container layout. The tablet's separate Data seed requires identity checks independent of any root-container role lookup. Neither binary was executed and the image was detached after inspection.

Follow-up arm64e disassembly resolves the dispatch. For `mount -P 1`, the Apple `mount` binary looks up `/` and, when its filesystem type is `apfs`, executes `/System/Library/Filesystems/apfs.fs/Contents/Resources/apfs_boot_util` with argv `1`. For `mount -P 2`, it reads `vfs.generic.apfs.rosp`; only a successful query with a nonzero value executes the same utility with argv `2`. The phase-2 utility receives no separate Data UUID and its embedded diagnostics describe finding Data by role in the APFS container for the root device. Thus stock phase 2 is not evidence that the independent Data seed will be mounted. The OS image's `mount` hash matches the inspected original helper. This remains disassembly-based; neither phase was executed.
