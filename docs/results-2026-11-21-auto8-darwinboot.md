The candidate replaces only the same-size FD in the timed Probe 2 image and recomputes the Android header ID. The retained firmware volume inventory contains DarwinBoot GUID `1B64AF87-8415-4B57-9B16-680D70913B9F`. The payload, shim and DTB match the previous probe. The offline reference verifier reported zero failures.

Stock ABL reported slot A successful and bootable, six retries, and no snapshot. It accepted `fastboot boot`. Subsequent USB checks through 13:32:25 found neither ADB nor Fastboot. The operator photo subsequently showed UniXNU 0.1.0 with the 8-CPU macOS entry selected and a return status of `Unsupported`. The menu footer reported `drivers 0 loaded / 0 failed`. A fresh host check still found neither ADB nor Fastboot. Firmware logs were unavailable, so the return site, XNU handoff and the 90-second reset remain unverified. The menu counter alone does not establish the state of DXE driver dispatch. ADB subsequently recognized the tablet and confirmed `OS3.0.309.0.WPYCNXM`, slot `_a`, and `sys.boot_completed=1`. The SHA-256 of `/data/local/tmp/piano-layout-20261121-check` matched the pre-run value. The recovery trigger was not observed, and post-run ABL success and retry values were not measured.

A follow-up comparison of the two generated FVMAIN volumes found the same 174 file GUIDs, including DarwinBoot in both. Thirty-seven file payloads differ byte for byte, including DarwinBoot and the UniXNU menu. Some differences may be build metadata. The earlier runtime message establishes that the loader protocol was unavailable when requested, despite the driver appearing in the firmware inventory. The whole-FD swap therefore does not isolate DarwinBoot dispatch.
